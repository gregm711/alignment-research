# A local discovery loop for learning which beliefs to revise

Optimize useful answers under a fixed observation budget. Our original [invoice control](../invoice-revision/README.md) is saturated. This development gym adds overlapping scopes, irregular probe menus and fallible reports. It exercises evidence selection and persistent state. A result here cannot establish a general architecture or a joule advantage.

## Before the first run

A reported invoice has an apparently reversed date. Five equally likely scopes are possible: false alarm, just this invoice, its supplier, its region, or its importer. Once per episode one of two reporters is selected. Their verified histories have eight observations from a reliability of 0.85 or 0.55. On 20% of episodes the two sources have since exchanged reliabilities, without notice. The current reporter endorses or disputes the original complaint, with accuracy determined by current reliability. Two independent receipts may be bought, each an always-correct answer for one probe invoice. The menus vary and can include redundant evidence. This is a drifting-source mixture across independent incidents, not a long-lived stream where reporters can be recalibrated over many incidents.

For every row, four binary features mean same invoice, supplier, region and importer as the reported invoice. A row sharing the invoice ID always shares all three other features. In this artificial procurement domain supplier, region and importer may otherwise overlap independently. The five hypothesized reversal labels are zero followed by those four bits. New invoices always have a different ID. Previously booked rows include the reported invoice. Every old booking initially contains the uncorrected date. A correct reversal also changes the calculated due date. The gym scores the reversal decision; the original calendar audit separately verifies exact dates.

The only candidate artifact is a Python file using the standard library with three functions:
- `step(observation)` returns a menu index to buy a receipt, or a hex string encoding final memory (empty is valid). At two receipts it must return memory. The observation contains `menu` (list of feature rows), `history` (correct counts out of eight for each reporter), `source` (0 or 1), `endorses` (boolean), and `receipts` (ordered [menu index, bit] pairs).
- `forecast(observation, row)` returns the probability of a reversal before the next verified receipt. All candidates forecast the same three randomly ordered menu receipts in sequence. Score mean binary log loss in bits, clipped at probabilities 0.000001 and 0.999999, and report loss at each depth. Candidate-chosen probes are graded separately. Receipt perplexity is two raised to bits per receipt.
- `answer(memory_hex, row, old)` returns integer 0 or 1 for keeping/reversing the date. For an old row the returned action is also the ledger update. Only saved memory (at most 32 bytes) and the row survive restart. Each evaluation stage gets a fresh isolated process. Treat episodes independently. No third-party packages, filesystem data, network or subprocesses. Return deterministic choices. Published costs include receipt count and serialized incident bytes. Fixed program size is recorded separately. Runtime and energy depend on hardware.

Compare an always-keep floor, random-order checking, and a belief-based active baseline. Prediction: informed probes improve balanced accuracy over random-order checking. Strong outcome: improve on the active baseline on the Pareto frontier for in-scope repairs, unaffected retention, false-alarm retention, fresh and old correctness, probe count, persisted bytes, and prequential bits per receipt. A tie or loss is reportable. Freeze hypotheses and candidate content before scoring, bound explorations, retain failures and do not claim a development win as a discovery.
