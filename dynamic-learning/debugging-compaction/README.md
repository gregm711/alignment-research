# Can a compacted debugging session still change its diagnosis?

## Stage 1 — instrument development, before model trials

The proposed public result needs real debugging sessions, independent model families, and runnable patches. Begin with a cheaper test of the measurement itself. Eight small Python compatibility repairs reconstruct plausible incidents around documented library semantics. Two possible reference behaviors produce identical ordinary examples and disagree on edge cases. Captured calls to two reference implementations survive in the prefix. The working hypothesis favors one reference. A later routing observation confirms it or overturns it. Both branches receive exactly the same prefix, source code and pre-fork note. The model gets no later expected output. A freely authored replacement function must pass hidden discriminating and ordinary regression tests. These fixtures are authored mechanisms, not recordings of production incidents.

Use a local Qwen2.5-Coder 7B Instruct for the screen. Generate fresh greedy outputs in independent sessions, using exactly the same context window and output cap. Generate the compaction note before revealing either branch. Make the first comparison among full history, ordinary summary, evidence-preserving summary, and no earlier history. Both summary policies have a 96-token cap using the writer's tokenizer. Compare actual token counts as well as the cap. Test same-length evidence restoration and transcript retrieval after the first screen identifies an eligible failure. Keep every answer and failure. Validate the scorer with buggy and correct implementations for both endpoints and check the resulting branch labels before collecting predictions.

Prediction: full history will solve both branches in at least four of eight cases. Ordinary compaction will cost at least two overturn repairs that pass with full history. We expect preserving competing evidence to rescue at least one. A case gets no credit for an effect if its full-history patch fails. If suffix-only performs as well, the task provides weak evidence that old observations matter. A success here justifies more realistic traces. Never count output samples or branch variants as independent bugs. Use local compute, record model identifiers and inference timings, and keep downloaded weights outside Git.

## Repair-interface check and evidence readout, registered before these trials

The first historical Qwen reader gave a provisional score_text diagnosis after inspecting both a screen row and a fresh row. Its ten repair attempts all failed the expression interface. Nine used an unsupported top-level key, and the remaining expression attempted to replace final-answer candidates with intermediate-step booleans. Retain those attempts. Run one additional turn on each arm with the same original source, its own failed edit, the interface error, and JSON-constrained decoding for the two legal keys. No held-out test details enter the retry. This measures whether one ordinary edit-feedback cycle removes the interface failure. It cannot establish persistence of the original diagnosis by itself.

On the controlled cases, test whether the models can report the selected archive's observation without writing code. Show the saved note, fresh route and the first discriminating input. This is recognition of an observation, not evidence of successful coding. It separates attribution and output selection from writing a generalizing repair.

## Selecting an executable repair, registered before generating candidate pools

The two readers reliably recognized some attributed observations but rarely applied them in their first patch. Test a different use of the same memory. Give Qwen only the function purpose, buggy source and shared smoke examples. Ask for four plausible distinct implementations that differ on edge behavior. Generate the pool once per case, independent of the archive labels, disputed outputs, later route and hidden tests. Every policy gets the same pool and the same spending on candidate generation. The source and candidates are generally available code, outside the persistent handoff budget; report their cost separately.

At decision time compare these policies on **all** cases: (1) the first candidate as a zero-memory baseline, (2) the first candidate passing the common-input record, (3) the first candidate passing the true attributed record, and (4) the first candidate passing the label-swapped record. Use source-order tie-breaking in every arm and fall back to the first candidate when no candidate passes. Also evaluate reversed candidate order and an oracle that may inspect hidden tests, solely as an upper bound on the pool. Hold out all scored inputs except the smoke regressions. Report how often the pool contains a passing candidate, how many candidates passed each check, and how often matching one example picked a patch that subsequently failed the hidden tests. Predict at least two more correct reversal patches from the true record than from the common record. Candidate screening is an exploratory design with extra search compute. This comparison estimates the effect of which equal-budget observation is kept at fixed search compute. Cross-model or new-case replication is required for a broad claim.
